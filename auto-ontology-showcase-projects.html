Shared method

Baseline

Every project compares 2 agents on the same questions:

  • Baseline: Claude with the raw schema only, writing SQL.
  • Auto-ontology: the same questions through ask_question (MCP) or POST /api/chat/completions.

Without a baseline, a demo shows only that SQL works. It does not show what auto-ontology adds.

Repeats

Compilation and answers come from LLMs and are not deterministic. Run each test at least 3 times. Report the mean and the range.

Ground truth

Write the correct answer for each question before the run. Keep the question set and the answers in a file next to this document.

P2 — "What is revenue?" in SEC data (first project) done

Goal

Test the main claim of auto-ontology on real public data that nobody cleaned for a demo. The README opens with it: "a revenue metric answered faster is worth nothing if the number is wrong."

Why first

  1. It tests the main claim of the tool: a correct revenue number.
  2. The data comes from real company filings. Nobody designed it for auto-ontology.
  3. The difficulty is real: one company can report revenue under several tags. A wrong tag gives a wrong number, and the query still runs without an error.
  4. Anyone can check each answer against the company's 10-K.
  5. It shows 5 features in one project: reconciliation, certification, provenance, refusal (P1) and learning (P5).

Data

SEC Financial Statement Data Sets. 4 tables: sub (submissions), num (numbers), tag (tags), pre (presentation), joined by the filing number adsh. Column names are cryptic. Revenue tags include Revenues and RevenueFromContractWithCustomerExcludingAssessedTax.

Method

  1. Data: download 1 quarter. Pick the first quarter of a year: most companies with a 31 December year end file their 10-K in February or March. Check the size of num before you load it. Load the tables into DuckDB or Postgres. Connect auto-ontology and compile.
  2. Answerable questions: pick 10 companies. Ask for revenue, net income and total assets for one fiscal year: 30 questions. Write each correct answer from the 10-K before any run.
  3. Questions the data cannot answer (P1 test): write 15 questions that need data not in the filings, for example stock price or analyst estimates.
  4. Questions you never correct: keep 10 of the 30 answerable questions apart. Never certify a correction for them.
  5. First runs: run all 45 questions through the baseline and through auto-ontology, 3 times each.
  6. Correction rounds (P5 test): certify corrections for the wrong answers. Run all questions again. Do 3 rounds.

Results to show

  1. Accuracy on the 10-K numbers: baseline, auto-ontology before certification, auto-ontology after each round.
  2. Correct refusals against invented answers on the 15 questions the data cannot answer.
  3. Accuracy on the 10 questions you never corrected.
  4. The SQL and steps of one answer, as the provenance example.

Risks

  • The result can go against auto-ontology. The baseline can do as well. Publish the result either way.
  • The correct answers take manual work: about 2 hours for 30 numbers. Do not take them from another XBRL tool: it reads the same tags and can make the same tag mistake.
  • Revenue tags differ by company and by year. The certified definition must handle more than one tag.
  • DuckDB is connection-string only (docs/connections.md). It cannot be added in the Settings screen.
  • Check whether the chat API refuses questions, or only the MCP flow with check_answerable.

4. Provenance example (R2, Amazon revenue, holdout, correct: 716,924,000,000). The answer came with this SQL:

SELECT n.value AS revenue FROM sec.public.num AS n JOIN sec.public.sub AS s ON s.adsh = n.adsh JOIN sec.public.tag AS t ON n.tag = t.tag WHERE s.name ILIKE '%AMAZON%' AND s.form = '10-K' AND s.period = '2025-12-31' AND n.tag IN ('Revenues','RevenueFromContractWithCustomerExcludingAssessedTax','RevenuesNetOfInterestExpense') AND n.ddate = s.period AND n.qtrs = 4 AND n.segments IS NULL AND n.coreg IS NULL AND n.uom = 'USD' ORDER BY CASE n.tag WHEN 'Revenues' THEN 1 WHEN 'RevenueFromContractWithCustomerExcludingAssessedTax' THEN 2 ELSE 3 END LIMIT 1

It is the certified "Fiscal Year Revenue" attribute with the company changed. The extra join to tag on tag alone (without version) did not change the value here, but it can repeat rows. The response text explained each filter. The runner did not store the step trace (thoughts).

5. What the result says.

  1. On these 4 raw SEC tables, the generated ontology did not help: 0 of 30 in A and in B, against 30 of 30 for the baseline. The baseline model (Claude Opus 5.5) is much stronger than the tool's default model (nvidia/nemotron-3.5-lightning-30b-a3b), so this compares 2 systems, not the ontology alone.
  2. Declared keys fixed the graph (0 to 6 correct links; the sub term named correctly) and raised refusals from 2 to 5 of 15, but made no number correct.
  3. Certified SQL definitions are the lever that worked: 3 definitions took the subset from 0 of 6 to 3 of 6 (R2), and 3 verified examples to 4 of 6 (R3); 2 of the 4 are holdout questions. Descriptions alone did not.
  4. Out of the box, the tool did not run against its default hosted model: structured output failed (HTTP 400 guided_json), and thinking overflowed the code's token limits. The 2-column FK cross product and the overlap-check plan (more than 19 min without an index) are defects that any warehouse with composite keys will meet.

Limits of this result. 1 repeat per auto-ontology measurement (rate limit), so no range. Rounds on 6 questions, not 30. Refusal after correction not measured. The MCP check_answerable flow not tested. The baseline's "no file reads" rule was by prompt only. The baseline grouped 15 questions per agent by metric, so it could reuse what it learned within a batch. The 3 metric definitions were checked against all 10 companies before certification, the 3 holdout companies included. So the holdout result shows that the agent applied a certified pattern to a new company name; it does not show that a definition written without knowledge of those companies carried over.

P8 — Scale test: when do definitions stop fitting in a prompt? done

Goal

P7 showed that the benefit is in the definitions: Claude got 11 of 11 with 13 definitions as prompt text (arm f), and the ontology added nothing. That result holds for a small set. P8 tests the claim that is left: when there are too many definitions for one prompt, does the ontology find the right one better than a plain search over the same definition text? If the ontology arm is not better than the plain search at any level, its retrieval adds nothing over a vector index on this data.

Scope

P8 tests retrieval only. It does not test governance, provenance, access control or the certification workflow. A P8 result must not be read as a result on those.

Data

  • Database cchist as in P7 (real rows), plus decoy tables with real rows that copy warehouse patterns: staging copies (stg_tool_call), period splits (tool_call_2026h1, human_message_2026q2), per-model views, archive copies with 1 column changed. Each decoy is a real table, so each decoy SQL gives a real number that is different from the target.
  • Decoy definitions made from templates over the schema, not written one by one: per model, per tool, with and without sidechain, per pattern-id range, per period, per decoy table. They share words with the targets ("failed Read calls including denied", "typed messages in staging"). This is how a real semantic layer is hard: many near-variant metrics, not random noise.
  • Each definition = name + description + SQL + truth computed by running the SQL. All are frozen in a file before any question is written.

Questions

  • 10 compose: the answer needs a new query from 1 or more definitions (as kill_by_pattern_opus48 in P7).
  • 15 near-variant: the correct target is a variant, and a more common definition is close. Catches "took the well-known one".

Arms (same model in every arm: Claude Opus 5.5, 3 repeats, claude -p --setting-sources local as in P7)

  1. P (prompt): raw DDL + all definitions of the level as prompt text (P7 arm f at scale).
  2. R (plain search): raw DDL + 1 search command that returns the top 10 definitions from an embedding search over the definition text. The agent can call it again with other words. Same hosted embedding model as auto-ontology (nvidia/nemotron-3-embed-1b). About 20 lines of Python.
  3. The agent writes its own SQL. The definitions are certified in the store (term descriptions + SQL attributes), as in P7 arm c.

Pass / fail (written before any run)

  • O shows a benefit at a level if O correct ≥ R correct + 4 and O ≥ P + 4 (of 40 answerable), with ranges that do not overlap over 3 repeats. At a level where P does not fit, only O against R counts.
  • Plain search is enough if R ≥ O at every level.
  • Refusal: each arm must refuse at least 4 of 5 unanswerable questions. Inventions are reported per arm.
  • Report per level and arm: correct per class, refusals, inventions, input tokens, cost, time.

  • The near-variant questions depend on correct decoys. Check before the runs: each near-variant target and its nearest decoy give different numbers.

Background: why not crm_v3

The first idea was to apply auto-ontology to crm_v3. The assessment on 2026-11-05 found these problems:

  1. crm_v3 already has a hand-written ontology: OBJECTS at app/db.py:26 (11 object types), and 22 links in FOUNDRY-MAPPING.html.
  2. Its main numbers come from Python in app/rules.py (signals, combined risk 1 − (1 − 17%) × (1 − 21%) = 35%, confidence penalties). The auto-ontology agent writes SQL only.
  3. It already has an MCP server (crm_read, crm_write) and a provenance screen.
  4. It is 1 SQLite file for 1 team. Auto-ontology's main purpose is reconciliation across systems.
  5. The SQLite connector's get_queries returns an empty table (auto_ontology/connectors/sqlite.py:175), so the SQL-attribute suggester has no input.
  6. The setup: crm_v3 needs 1 pip package. Auto-ontology needs Docker Compose, Postgres with pgvector, Next.js and an API key.

Kept for later: crm_v3 is a usable test of link discovery. It declares no foreign keys (app/db.py:260), and its role-named links (owner_id→sales_reps, contact_id→people, past_company_id/new_company_id→companies, new_person_id→people) do not follow the naming rule in auto_ontology/semantic/fk_suggester.py.
