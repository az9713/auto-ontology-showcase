SEC data: the ontology map

Database sec: SEC Financial Statement Data Sets, 2026q1. 4 tables, 65 columns. Sources: data/sec/load_sec.sql, p2/model_A.yaml, p2/model_B.yaml, p2/corrections.py, and read-only queries on the live database (2026-11-06).

The picture in one sentence. A filing (sub) holds many facts (num). Each fact is one number for one concept (tag) and one period. A statement line (pre) records where the filer printed that concept, and the filer's label for it.

4. The traps in this data

  1. One concept, several tags. Revenue is Revenues for 6 of the 10 companies, RevenueFromContractWithCustomerExcludingAssessedTax for Amazon and Tesla, and RevenuesNetOfInterestExpense for JPMorgan. Net income for Caterpillar is NetIncomeLossAvailableToCommonStockholdersBasic. A wrong tag gives no error.
  2. Most tags are company-specific. 83,919 of 91,794 tag rows (91.4%) have custom = true. For these rows, version is the filing's adsh, not us-gaap/2025.
  3. The key of tag has 2 columns. One tag has one row per taxonomy version. A join on tag alone can repeat rows. Join on tag and version.
  4. Breakdowns sit next to totals. For Amazon revenue: 18 rows at the year end, 1 company total. Filter segments IS NULL and coreg IS NULL. A sum gave Coca-Cola revenue 18,775,436,000,089 in condition A.
  5. Period type. qtrs = 4 is a full year (revenue, net income). qtrs = 0 is a point in time (total assets).
  6. Labels are not names. pre.plabel is the filer's own text ("Total net sales"). Select amounts by num.tag, not by label.
  7. Company names. sub.name is upper case and exact. The 2 failures left after R3 were name matches: ILIKE '%BERKSHIRE HATHAWAY%' matched other filers, and 'WALMART INC' missed the period.
  8. Not every filing is annual. 4,262 of 6,169 filings are 10-K; 972 are 10-Q, 372 20-F, 112 40-F.

5. Ontology or database: is there a difference?

Yes, but the line between them is not sharp. A database stores the rows and checks that each row and each query has a valid form. An ontology stores what the rows mean and the rules to get a correct number from them. The database answers "is this query valid?". The ontology helps the agent answer "is this the right query?".

The test case from P2. Condition A gave Coca-Cola revenue as 18,775,436,000,089: a sum over many tags and filings. The database ran that query with no error, because the SQL was valid. Only a rule about meaning ("a company total is one row; never sum across tags") marks it as wrong. That rule is in the ontology (the R1 description of num), not in the database.

Database (sec)Ontology (auto-ontology, p2/model_B.yaml + R1–R3)
What it holdsTables, columns, types, rows. Keys, if someone declares them. Terms (1 per table), column attributes (name + description), links, SQL attributes (metric definitions), custom analyses (verified example queries), and a certified flag on each item.
Who reads itThe database engine, on each query and each write. The agent (an LLM), when it writes the SQL for a question.
Is it enforced?Yes. A row that breaks a key or a type is rejected. No. It is advice. The agent can ignore it: after R3, the agent matched 'WALMART INC' exactly and found no row, although the certified sub.name description says "Match with ILIKE on the distinctive word".
Table num10 columns; value is numeric(28,4). "Reported Financial Fact": one number for one tag, one period, one filing. Never sum across tags.
Column qtrsAn integer, values 0 to 4. "4 = one full fiscal year (revenue, net income). 0 = a point in time (total assets)."
"Revenue"Not an object. It is 3 of 91,794 tag names, and the data does not say which one applies to which company. SQL attribute "Fiscal Year Revenue": the tag priority, qtrs = 4, company total. One definition for every company.
Link num → subForeign key num_adsh_fk (only in condition B; the SEC files declare none). A link on adsh. In B it came from the declared key. In A the tool did not find it.

Where they overlap.

  • A schema is a small ontology already. A foreign key states a relation ("a fact belongs to a filing"). In B, the 6 links came directly from the 4 declared keys.
  • The ontology is itself stored in a database (database auto_ontology in the same Postgres container, tables such as term, sql_attribute, custom_analysis). The difference is the content (meaning and rules) and the reader (the agent), not the storage.
  • The word "ontology" has 2 uses. In formal knowledge engineering (OWL, RDF), an ontology has classes, properties and logical axioms, and a reasoner derives new facts from them. The auto-ontology model has no axioms and no reasoner. Its top-level parts are data_layer and semantic_layer (terms, links, SQL attributes, custom analyses). That is the type of model that tools such as dbt metrics or LookML call a "semantic layer".

What P2 measured about the difference. Meaning in plain text did not change the result: R1 (certified descriptions) gave 0 of 6. Meaning written as SQL did: R2 (3 certified SQL attributes) gave 3 of 6, and R3 (3 verified examples) gave 4 of 6. In this test, the ontology was useful only where it stated a rule in a form close to a query.
